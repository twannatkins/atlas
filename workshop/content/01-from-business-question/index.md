# Module 1 — From Business Question to Ontology

## Learning Objectives

- Extract nouns and verbs from a financial services competency question and sort
  them into ontology classes, properties, and instances
- Explain the difference between a class (independent identity, referenceable)
  and a property (describes another thing, no identity of its own), and apply the
  distinction to the three hard cases in the wealth-signal domain
- Write constraints in plain English before encoding them in OWL or SHACL, and
  understand why the plain-English form is itself a deliverable for MRM reviewers
- Verify that all seven starter competency questions return non-empty results from
  the starter ontology, confirming the ontology is traversable by the questions
  that motivated it
- Read the `ontology/atlas-core.ttl` file and trace every class back to at least
  one competency question using `ontology/rationale.md`

## Time Estimate

30 to 45 minutes.

## Prerequisites

- A running SageMaker Studio or SageMaker Studio Classic notebook instance with
  this repository cloned
- Amazon Bedrock enabled in us-east-1 with the SageMaker execution role granted
  `bedrock:InvokeModel` for the `us.anthropic.claude-sonnet-4-6` cross-region
  inference profile (pre-configured in the workshop environment)
- No prior ontology experience required

## What You Will Build

This module produces two deliverables:

1. `ontology/atlas-core.ttl` — already present in the repository; you will read
   it, understand how it was derived, and optionally extend it with concepts from
   your own domain
2. `ontology/rationale.md` — generated by running cell 23 in
   `notebooks/01_journey_to_ontology.ipynb`; a Markdown table linking every class
   to the competency question(s) that justify it

The starter ontology contains 18 OWL classes and approximately 30 properties.
It is intentionally small. The anti-pattern — boiling the ocean by modeling every
concept before any consumer touches the graph — is explicitly called out in the
notebook.

### Step 2 — Read the competency questions

Read the seven competency questions in cell 4 aloud. Do not skip this step.
The questions are written in business language intentionally. Notice:

- CQ1 uses the phrase "Consumer-side customers" — this is a business segmentation
  boundary, not a database join key. It becomes a property pattern in the ontology.
- CQ2 asks for both the "deterministic component" and the "probabilistic component"
  of a score — this is the first signal that `Score` cannot be a simple decimal property.
- CQ6 mentions a regulator asking a question about audit trail. This implies the
  audit chain must be queryable end-to-end in SPARQL.

## Troubleshooting

**Cell 16 fails with "No such file or directory" for atlas-core.ttl**

The notebook expects to be run from the `notebooks/` directory with the repo root
one level up. Verify your SageMaker notebook is opened from the correct path.
Check that `../ontology/atlas-core.ttl` resolves relative to the notebook's
working directory.

**Cell 14 raises `RuntimeError: Bedrock AccessDeniedException`**

The SageMaker execution role is missing `bedrock:InvokeModel` permission for the
`us.anthropic.claude-sonnet-4-6` cross-region inference profile. In IAM, add an
inline policy to the execution role granting this action on the inference profile
ARN, then restart the kernel and re-run.

**Cell 14 raises `RuntimeError: Bedrock ResourceNotFoundException`**

Cross-region inference is not enabled in your account or the profile ID is wrong.
In the AWS console, navigate to Amazon Bedrock > Model access and confirm that
Anthropic Claude models are enabled in us-east-1. The model ID must begin with
the `us.` prefix (`us.anthropic.claude-sonnet-4-6`, not the bare model ID).

**Cell 14 raises `RuntimeError: Bedrock ValidationException`**

The request body failed Bedrock's input validation. Confirm you are using the
`bedrock-2023-05-31` API version string and that the `messages` array is
correctly formatted. This is most commonly caused by editing the prompt constant
to include an unsupported Unicode character or an unterminated string.

**Cell 25 fails Gate 2 with "missing rdfs:comment" violations**

If you have modified `atlas-core.ttl` to add classes and did not add `rdfs:comment`
or `skos:definition` to each new class, Gate 2 will fail. Every class in the ontology
must have a human-readable justification — this is the "rationale gate" in code.

**Cell 21 fails with "CQ7: FAIL (0 rows)"**

The CQ7 query joins `atlas:hasAuditRecord` and `prov:wasDerivedFrom`. If the
instance graph construction in cell 20 failed before building the AuditRecord node,
the join returns zero rows. Re-run cell 20, then cell 21.

## Extending This to Your Data

The five-step journey in this module applies to any domain where you need to build
an ontology that a regulator or a model risk management reviewer will need to understand.
Write three to seven competency questions in your line of business's language, follow
the five steps, and compare your resulting class list to `atlas-core.ttl`. Most readers
find approximately 60% overlap — the FIBO-aligned core classes — and 40% divergence,
which is where their institution-specific concepts live. That divergence is what
Module 2 — FIBO Alignment and the Extension Ring teaches you to model correctly.

## What's Next

Module 1 produced the ontology. Module 2 asks a harder question: how much of this
ontology already exists in FIBO, and what does it mean to bind your classes to FIBO
IRIs rather than just naming them independently? The answer matters for interoperability,
for reasoner behavior, and for the SHACL shapes that Module 6 will enforce — because
a SHACL shape that asserts a constraint on `atlas:Customer` and a shape that asserts
the same constraint on `fibo-fnd-pty-pty:IndependentParty` are not the same shape,
and the difference has operational consequences for compliance.
